The copperhead console is about to get a conversation view, and in the version we have
built every message becomes a run. A short list of verbs decides which kind: a message
that asks to look and asks for nothing to change is a `check`, and anything else is a
`do`. There is no way to ask a question that is not a job, and no way for the platform
to reply with a plan before it starts work on a change.

What we want above it is a conductor: one conversation that can answer a question, read
the repository, write a plan and launch any of the CLI's four kinds of run. That is an
agent harness, and several teams have already built serious ones. Before writing a
design we read how Claude Code, Codex and the open-source harnesses do it, through their
documentation, their source where it is open and the pull requests where they changed
their minds.

They mostly agree. Where they do not, one constraint of ours decides before taste gets a
say, so that comes first.

## The constraint that picks between them

A model provider key lives in one component of copperhead's hosted platform: the gateway
every model call passes through. It is not in the web app, and it is never in the
container that runs the CLI against your repository, because that container executes
whatever your repository contains. A key you bring is stored encrypted, out of reach of
anything that runs your code. A run carries a short-lived credential that the gateway
accepts and that stops working when the run ends.

Any design that runs the agent loop inside the sandbox has to put a model credential in
there with it. That is the first thing to check about a harness, and it sorts them
quickly.

## The loop runs outside the sandbox

Vercel's [open-agents](https://github.com/vercel-labs/open-agents) template puts it in
two sentences: "Chat requests start a workflow run instead of executing the agent
inline" and "The agent does not run inside the VM." Its lessons-learned notes give the
reason for the first, which is that lifecycle work started inline in serverless code is
not durable. [Open SWE](https://github.com/langchain-ai/open-swe) runs its loop on a
LangGraph server and treats the sandbox providers it supports, Modal, Daytona, E2B and
others, as places that execute commands.

[smolagents](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution)
describes the problem from the other side. Remote sandboxing, its documentation says,
"doesn't support multi-agents", because a model call made inside the sandbox "would lack
credentials". OpenHands V1 appears to go the other way: the request that starts a
conversation sends the agent, model settings included, to an agent server that runs with
the workspace, so the loop and the credential sit where the commands run. For one
developer on their own machine that is a reasonable trade. For us it is the arrangement
the constraint above rules out.

So the conductor is a warm service that executes no customer code, reaches models
through the gateway like everything else and does not live inside a web request. The
durable part Vercel reached for a workflow engine to get, we already have: runs are
queued in Postgres, claimed with a lease and reaped when a worker stops answering.

## Launch the run, end the turn

The harnesses we read delegate in much the same way. A task tool opens a child session
with a fresh context, its own instructions and a narrower set of tools. Only the child's
final message comes back to the parent. In Claude Code that is the Agent tool. In Codex
each child is a thread of its own, opened with `spawn_agent`, then waited on, messaged
and closed by three sibling tools. The `task` tool in
[opencode](https://opencode.ai/docs/agents/) creates a linked child session that can be
resumed by its id.

Where they differ is what the parent does while the child works, and that is where long
jobs live. When opencode runs a subagent in the background, the tool description tells
the model "You will be notified when it completes" and, in capitals, not to sleep or
poll. deepagents polls its async subagents instead, and [its
documentation](https://docs.langchain.com/oss/python/deepagents/async-subagents) lists
what goes wrong when a model does the polling: checking immediately after launch, citing
a status it read earlier in the history, mangling the task id, exhausting the pool of
workers.

A hosted `do` run is allowed thirty minutes and a `create` run an hour. A conversation
turn held open that long keeps a model context and a server process waiting, and invites
the failures on the deepagents list. So the conductor's launch tool starts the run and
the turn ends. When the run finishes, its result lands in the thread as a new item. That
item starts the next turn.

This is the largest change the reading made to our first sketch, in which the launch
tool waited for its run inside the turn.

## One agent, with the gates in code

Two of the best-known designs that put a router in front of the agent were retired this
year. Roo Code's Boomerang orchestrator could not read files, write them, use MCP or run
commands, so it delegated everything. Roo was archived in May, and Kilo, whose CLI is
now a fork of opencode, marks its own orchestrator mode deprecated because agents with
full tool access "now support subagents natively". Open SWE's first version put a
manager graph in front, which classified each incoming message into one of seven routes
and handed the work to separate planner and programmer graphs. In February its
maintainers deleted the manager, planner and programmer graphs and rebuilt on deepagents
as a single agent.

What that agent has instead of a router is structure. While Open SWE's plan mode is on,
middleware recomputes the tool list for each model call and leaves the mutating tools
out until a plan is approved through an `approve_plan` tool. A separate guard holds any
push that touches the repository's CI workflow files until a person approves it. The
model is not asked to hold back from editing. The editing tools are absent from the
request.

The copperhead CLI already works this way. Its edit tools stay out of the tool list
until a change proposal validates, and [a
test](https://github.com/copperheadhq/copperhead/blob/main/test/gating-sync.test.ts)
keeps the list and the gate in step. The conductor gets the same treatment one level up.
There is no classifier stage, and the tools that launch a `do` or a `create` are missing
from its tool list until you have approved its plan. The list of verbs that picks a run
kind today goes away.

## Approval follows the tool, and it is stored

Harnesses disagree about whose call an approval is. Cline lets the model set a
`requires_approval` flag on its own command. Vercel tried heuristics over shell commands
and reported "too many false-positive approvals". Both leave the decision somewhere a
model or a guess can move it, which is tolerable on a laptop and is not tolerable when
many organisations share one product.

The designs we are copying decide by the class of the tool, on the server. In Codex an
approval is a request from server to client that pauses the turn until someone answers
accept, accept for the session, decline or cancel. When it resolves, every other
connected client is told. opencode sets each tool to allow, ask or deny. When a person
rejects a call with a message attached, the message goes back to the model as a
correction. The Vercel AI SDK can sign each approval request with an HMAC when it is
issued and verify the signature when the answer comes back, so a client cannot forge
one.

Hosted `do` runs are gaining an approval step before they push to your repository. The
request is a row in the database, and it is resolved by a function that checks the
person answering belongs to the organisation, never by a write from the browser. The
conductor generalises it. A plan gets an approval of its own beside the push. Either can
be accepted once, accepted for the rest of the thread or declined with a note that goes
back to the conductor. Everyone watching the thread sees the answer when it lands.

## Skills are a file format now

A skill is a folder holding a `SKILL.md`: a name, a description and instructions. The
format is published at [agentskills.io](https://agentskills.io/specification), which
lists Claude Code, Codex, GitHub Copilot, Cursor, Gemini CLI, opencode, OpenHands and
Goose among the tools that read it. The name is 1 to 64 lowercase letters, digits and
hyphens, matches its folder and cannot start or end with a hyphen. The description is at
most 1,024 characters. Codex and opencode both look in `.agents/skills`, and opencode
reads `.claude/skills` as well.

Until a skill is chosen, only its name and description sit in context. Codex gives that
catalogue 2 percent of the context window, or 8,000 characters when the window is
unknown. When the catalogue overflows, it shortens descriptions and then drops them.
Slash commands have folded into the same system. Codex deprecated its custom prompts in
favour of skills, and Claude Code marks a skill as user-only or model-only with a
frontmatter flag instead of keeping two mechanisms.

We are adopting the format unchanged and reading `.agents/skills` from the connected
repository, where the first sketch had invented a `.copperhead/skills`. A slash command
is a skill a person can invoke, plus a handful of built-ins. A skill can narrow the
conductor's tools but not widen them. OpenHands adds a skill when the agent touches
files matching a path, and a skill that loads footprint rules the moment a `.kicad_pcb`
is opened is the first one we want.

## A thread holds turns, and a turn holds items

Codex publishes the most complete protocol of the group. A thread holds turns, and a
turn holds items: an agent message, a plan, a command execution, a file change, a
context compaction. Each item announces that it started, streams deltas and then
completes. The completed form is the authoritative one. Starting a turn returns at once,
and a running turn can be steered or interrupted.

The server holds the truth in these designs, and clients come and go. opencode is built
that way even on a laptop, with one server, one event stream and a terminal interface
that is only another client of it. Goose removed its own REST server in July and now
serves the Agent Client Protocol over HTTP and WebSocket instead.

The conversation view we have built already freezes a finished turn into stored blocks
and serves run events as a stream, so this is less a new design than a name for one we
have. The name matters because the conductor's own turns and the runs it launches should
render through one vocabulary, and the CLI's [run protocol
stream](https://github.com/copperheadhq/copperhead/issues/258) should emit the same
shapes.

## Keep the prefix still

OpenAI's January account of the Codex agent loop describes each request as the previous
request with new items appended. Changing the tool list, the model, the sandbox or the
working directory partway through a thread breaks the prompt cache, so configuration
changes arrive as new messages instead. Codex stores compaction as an item in the
history, and Claude Code marks the same moment with a boundary event. The Claude Agent
SDK stops a loop at a turn limit or a spend limit and reports the cost with the result.

The managed models we meter bill by the token, so for us this is a pricing decision
before it is an engineering one. Loading a skill appends its body as a message and never
changes the tool list. Compaction is stored like any other block. Every conductor turn
has a cap on model calls and a spend ceiling, checked against the organisation's
allowance before the model is called.

## Borrow the vocabulary, not the binary

The obvious question was whether to adopt one of these loops outright. The Claude Agent
SDK has the most mature loop, with skills, subagents and a session store, but it is made
for Claude models and built around file and shell tools the conductor must not have,
while our gateway serves models from several providers through one OpenAI-compatible
route. The Codex App Server has the best protocol, but it is a Rust binary that expects
to run inside the environment it works on. Its methods are still moving too:
`thread/rollback` was removed from it this month.

That leaves two candidates. One is the Vercel AI SDK's tool loop, which is TypeScript
like the rest of the platform, talks to any provider through that compatible route and
has tool approval built in. The other is a thin loop of our own. Once approvals,
persistence and budgets are ours anyway, the two come to about the same work. We have
not chosen between them. Either way the item vocabulary comes from Codex and the skill
format is the open one.

## What this does not settle

None of this is built. The conductor is a design, and this post describes what the
reading changed in it, not how it behaves.

The reading was of documentation and source, not of running systems. openai.com refused
our requests, so OpenAI's own posts about Codex were read through secondary summaries.
The prefix and cache behaviour above comes from them. The protocol and skills details
were checked against the Codex source at commit `1715e55`, which has already moved past
the January account in one respect: its WebSocket path now sends a previous response id,
which that account said Codex avoided. That OpenHands V1 hands the model settings to its
sandbox is read from the request that starts a conversation, not traced end to end.
Every claim here about another project was checked a second time against its source or
documentation on 13 September, and the ones that did not hold were corrected or cut.
These projects change monthly, and some of what is quoted here will have moved by the
time you read it.

Two questions the reading could not answer, because they are ours: how a conversation
that launches no run is metered, and whether a plan approval is always required or is
something an organisation opts into.
